# 数据功能：用户规划的文献清单工作流

以 `../assets/数据功能工作流_执行版.drawio` 的 S1–S4 和决策点顺序为主轴。执行版在 v12 同步了 C1/S1.4 定义、S4.1 能力汇报、终点冻结与建模接口判定；v13 增补 S1.3 多版本核验关、框架确认（闸门 A）骨架继承快速路径与 SYS-UserPrior 用户先前工作继承通道；v17 起 assets 执行版图已按本文件重绘同步（含三分类登记、报错信号与返工回路），图文一致，二者任一修改须同步另一方；原图仍保存在用户提供的位置。本文件记录用户对图中术语的确认及执行所需的输出条件；不得从图的坐标、颜色或箭头自动推断科学事实。核心对象、五级数据层级与可采用标准统一定义于 `data-framework.md`。

用户决策点以具体决策内容命名，字母代号仅作别名（对应流程图节点）：框架确认（闸门 A）、冻结确认（闸门 B）、建模接口判定（闸门 C）。范式三分类判定在框架确认时登记，功能三的建模路线决策复用同一分类（见文末专节与 SKILL.md F3 条目）。

| 图中步骤 | 动作 | 最小输出与下一步 |
| --- | --- | --- |
| S1.1 | 询问研究课题、对象、拟评价方法和科学问题 | 足以作相关性初筛的课题摘要；不要求此时完成全部方法参数；**不存在"不分配/不替代"的直通情形**——若课题看似无需处理联产品负担（如"只记录全产品系统"），视为错误信号：联产品的共同上游负担必有处置（分配或替代），核对文献实际做法并如实向用户汇报 |
| S1.2 | 审查文献与课题相关性、清单覆盖和计算模型透明度 | 报告该来源能否支撑本课题；支撑不够则回到开始重新对齐课题，不擅改课题方向；各审查维度答案（范式／数据类型／功能单位可否换算／边界重合／副产品处理／背景库／数据来源／质量）汇总后与课题模型需求比对；硬不匹配（如功能单位不可换算）即如实汇报，不纳入框架候选；审查发现文献质量很差→如实汇报，由用户重新找文献（重新进入文献搜索环节） |
| S1.3、C1 | 核验主文、附件、代码及原始数据 | C1"有完整生命周期清单？"仅检验整链清单及其可追溯附件是否存在，不等于参数齐全；缺原始清单时具体报告并请用户补充；同一资料存在多版本时按内部标识＋关键单元格内容指纹判定权威版并全部登记（文件名、下载日期不算证据，见 `source-and-candidates.md`） |
| S1.4、C2 | 按"是否有完整生命周期清单"划分两池 | 分类依据是整链清单存在性，不是参数齐全度；每个来源体系的角色、依据和依赖；完整清单池为空则继续审查/补充，不转纯建模；用户先前工作结论以 SYS-UserPrior 登记，数值须回指原始证据 |
| S2.1 | 初读文章和数据，拟定分文献整理方案 | 目标 ALCA/CLCA、物理前景范围、功能单位、边界、主副产品处理、背景接口与来源适用性；环境/经济/社会结果核算不属于本 Skill |
| S2.2–S2.3 | 从完整清单池选框架参考文献，只确定单元操作流程结构 | AI 按 S1.2 各维度汇总比对结果推荐最合适的框架（附理由与候选差异），报用户确认（框架确认／闸门 A）；确认后汇报产品系统/模块/操作集合和主支线；此关不批量抓参数 |
| 框架确认（闸门 A） | 用户确认或否决 AI 推荐的框架；确认时登记范式三分类（同属 CLCA／同属 ALCA／不同）与分配/替代关注口径 | 否决则记录理由，换池内候选；候选耗尽就报告并等待补充/决定，不建立纯建模分支。通过后未选完整清单文献自动并入参数池，同时保留其完整清单候选身份；用户已有经确认的上一版骨架时，经一致性复核并留痕可继承沿用，不从零重画 |
| S3.1–S3.2、C3 | 读取原文功能单位、边界并与已确认框架比对 | 自洽性问题登记`问题与决策`；不受影响部分可继续，关键口径不自行裁决；显式询问用户所需系统边界是否比文献边界更窄，是则按裁定裁剪过程与流、登记边界决策并同步裁剪能耗/清洗/资本品等关联数据；边界项显式询问：资本品（设备/部件级材料按天摊销）是否纳入、原文标注为背景的过程（如废水处理）是否计入前景 |
| S3.3 | 按证据作最小黑箱判定和模块化划分 | 计算过程/可辨操作层级表及参数覆盖度矩阵（五级数据层级见 `data-framework.md`）；分别报告直接操作量、公式可拆量、过程/模块总量、仅拓扑与缺失。划分以文献自身的模块/步骤结构为依据；分不出依据的单元标**待定**——不阻塞流识别：先找全所有流，流的归类后置处理 |
| S3.4 | 逐过程识别全部输入、输出、内部转移和循环 | 流清单和端点、方向、边界、归属层级；不能把内部流重算为外部总量；过程总量不得伪装成操作量 |
| D1、S3.5 | 判断每条流是否需公式运算；公式流递归溯源 | 作者公式/代码版本、输入参数 ID、单位基准、代表情景和结果依赖；未得到所需参数则列缺口，不臆算 |
| S3.6–S3.7 | 逐流记录来源、去向、类型与量/公式链，全部流命名规整 | 稳定流 ID、按"归属单元＋来源—去向＋类型"的显示名称、证据位置和采用状态；名称不作关联键 |
| QC | 检查物料/水/能量、覆盖度与逐流记录完整性 | 覆盖度按五级数据层级评定；含**能源完整性主动核查**：电力/热逐过程"有/无/在哪"列表，缺口主动汇报，不等用户来问；有问题返回对应步骤复查；复查后仍有问题立即向用户汇报对象、证据、影响和建议选项，等待决定。不设固定复查次数或自动退出 |
| S4.1、冻结确认（闸门 B） | 汇报数据支撑能力结论＋模块化清单＋覆盖矩阵＋问题表和待补参数 | 能力汇报按 `data-capability-handoff.md`，含能画什么图、到什么精度、禁止的推断；用户确认清单与待补项；不确认则按指定缺口返工重报。确认只冻结获批准的科学范围，不能把待补关键值标为已完成 |
| S4.2 | 输出《待补参数清单》并冻结工作簿 | 冻结确认记录＋`validate_workbook.py --freeze` 通过；工作簿状态转 `frozen` |
| 建模接口判定（闸门 C） | 判定建模接口条件（满足其一：多源采用／自有决策／自有方法口径） | 具备→S4.3；不具备→仅交付冻结清单，不输出建模接口，避免单文献复现被包装成目标研究模型 |
| S4.3 | 输出建模接口说明 | 冻结清单表 → Brightway2 结构（activity/exchange、前景/背景接口位置、参数命名对应）的映射说明；不计算任何 LCIA/LCC 结果 |

## 文献池及来源依赖

文献池按来源体系的用途分类，不按 PDF 文件数分类。主文、补充材料、代码及同作者公开表格可以共同证明一篇文献的完整生命周期清单；它们共享一个来源体系 ID。`完整清单文献池`表示可被考虑为整链框架，`参数选取文献池`表示可为特定参数/流提供候选值或局部拓扑证据。同一来源可兼任；框架确认（闸门 A）通过后，未选的完整清单文献自动并入参数池，不删除其完整清单候选角色或覆盖来源证据。

## 框架文献维度比对打分机制（v17 新增）

S1.2 的审查答案同时是框架推荐的打分输入。对候选框架的每篇文献（完整清单池内）逐项回答下列维度，与用户课题模型需求（S1.1 三问答案）比对：

| 维度 | 比对内容 |
| --- | --- |
| 建模范式 | ALCA／CLCA 与课题范式是否一致 |
| 数据类型 | 平均数据／边际供应商数据与课题建模范式是否配套 |
| 功能单位 | 与课题功能单位是否相似、可否换算 |
| 系统边界 | 与课题边界是否重合，收窄是否可行 |
| 副产品处理 | 分配还是替代；若分配，经济／按质量／按蛋白质因子等系数是否满足课题需要 |
| 背景数据库 | 所用背景库（如 ecoinvent 版本、区域）与课题计划的兼容性 |
| 数据可追溯性 | 工厂实测还是文献引用值；附件、代码、公式透明度 |
| 文献质量 | 期刊、作者、发表时间 |

打分：每维度 2＝直接匹配，1＝可协调（换算、裁剪边界、调整接口后可用），0＝不匹配或未知；未指定权重时等权，用户可在 S1.1 或审查时声明重点维度加权。**否决项：功能单位不可换算等 S1.2 判定的硬不匹配——不进入打分，直接汇报用户。**

输出：逐篇维度打分表＋逐项理由（md 记录写 obsidian，同时作为文献分类与参数池后续使用的依据）→ 推荐总分最高者并附选择理由 → 框架确认（闸门 A）用户确认。用户否决或发现维度遗漏时，更新打分表后重新推荐。

## 范式三分类与分配/替代关注口径（v17 新增）

框架文献与课题的范式一致性在框架确认（闸门 A）时即判定登记——S1.2 已逐篇审查文献范式，S1.1 已知课题范式，无需等到冻结后。三分类及文献分配/替代做法的处理口径：

| 情况 | 文献的分配/替代 | 口径 |
| --- | --- | --- |
| ① 同属 CLCA | **必须关注**：替代接口是模型组成部分，登记为方法证据并列为功能三默认继承候选；是否沿用由用户确认 | 记录义务不豁免 |
| ② 同属 ALCA | **必须关注**：分配因子直接决定归因结果，登记；沿用或换政策（经济／质量／蛋白因子等）由用户确认 | 同上 |
| ③ 不同（文 ALCA→课 CLCA；文 CLCA→课 ALCA） | **不关注其分配结果／替代信用**：已分配负担或替代收益不得进入课题模型；做法登记留档作对照证据；课题的替代接口／边际供应商或分配因子在功能三由用户决定重建 | 证据仅作"为什么不用"的答辩留档 |

以上口径在所有课题统一适用：文献的分配/替代做法一律登记为方法证据，按三分类决定后续待遇；关注不等于采用，采用永远经用户确认。**不存在"不分配/不替代"的直通情形**——若判断某课题无需处理联产品负担，视为错误：核对文献实际做法（必有分配或替代）并如实向用户汇报。功能三的建模路线决策复用本三分类（见 SKILL.md F3 条目）。

## 返工和状态

- `C1 否`：报告缺少的原始清单文件及影响，请用户补充。`C2 否`：继续相关来源审查或等待用户补充，不转纯建模。
- `框架确认（闸门 A）否`：记录否决原因、评估其他完整清单候选；没有候选时向用户报告，不自行另起模型路线。
- `d_c3 不完善`：重新审查选定框架文献及相关数据是否完善；不完善→登记缺口清单、请用户补充（优先用户进行），不填猜测值、不以其他版本数据顶替。
- `C3 否`：把具体冲突列入问题表，区分对已确认框架及各流的影响；不受影响的逐流分析可继续。
- `D1 需要公式`：递归到原始参数；公式节点、参数节点、派生结果和流 ID 均保留可追溯关系。
- `QC 否`：返回缺流、缺参数、缺记录或平衡解释的对应步骤。复查仍有问题即及时报告，不因"复查一次"自动退出或标通过。
- `冻结确认（闸门 B）否`：按用户反馈返工并更新受影响下游。`冻结确认（闸门 B）是`：交付已确认范围、待补参数清单并冻结；冻结检查通过才可进入建模接口判定（闸门 C）与绘图功能。
- `建模接口判定（闸门 C）否`：流程以冻结清单收尾，数据清理与模块化整合目的已达成；建模由研究者自行处理。
- 冻结后更换框架（v17 新增）：视同框架确认否决处理——记录理由，按维度比对打分机制在完整清单池内重选，无可换候选则报告并等待用户扩大搜索，不自动转纯建模。新框架经框架确认（闸门 A）后重走 S2–S4，重新 QC、重新冻结交付。

固定的交付区分是：数据功能 Excel 是采用数值与公式的唯一事实源；模块化清单、覆盖度矩阵、问题标记表和待补参数清单可在该工作簿中呈现或由它导出，不建立第二套可手填的科学值。能力汇报按 `data-capability-handoff.md`，Excel 字段按 `excel-schema.md`，数值审查按 `calculation-audit.md`，对象与状态定义按 `data-framework.md`。
